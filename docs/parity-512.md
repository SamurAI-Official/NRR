# Parity: the head-to-head table

Generated by `tools/parity_harness.py` - **do not edit by hand**. Regenerate with:

```powershell
powershell -File tools\run_parity.ps1 -Nrr -Xess -Dlss
```

Scene: **all val scenes** (`models/training-data/godot-mid`, val split, 14 frames, 2.00x). GPU: NVIDIA GeForce RTX 4070 Ti, driver 610.88. A timing taken on a host doing other work is a timing on a busy host.

`same-frames` is the column that decides what a row may be used for. **yes** means the arm
was driven from this scene's own frames and scored against this scene's own targets, so its
row is a quality comparison. **no** means the arm ran in its own runtime on its own content,
so its row is a capability and latency measurement and its quality columns are empty by
construction. No sentence about quality may span a mixed pair.

The offline arms are driven from the `input` plane the scene's own frames carry; `nrr` is the
named model, fed exactly what the trainer exports.

A model's row names the inputs its export declares, because that is what makes the row
interpretable - the same weights fed a different input set are a different arm:

* `nrr` = `color,jitter,scale`
